# GitHub projects

Nakama can import an existing GitHub repository into its selected Windows workspace, link an existing managed Git checkout, inspect changes, fetch, pull a fast-forward update, create a reviewed local commit and request a reviewed push. Android sends these requests to the paired PC; it does not run Git or receive account tokens. Every push requires fresh approval in Windows Activity & approvals because repository automation may deploy, spend credits or send notifications.

## Setup and supported repositories

1. Install Git for Windows. The implementation and disposable repository tests support the installed Git 2.29 command set; keep your Git installation maintained separately.
2. In Windows Connections, save a labelled GitHub account token in the protected credential vault. Select that exact account when importing or linking. The account must have access to the repository; organisation approval, SSO, token permissions and branch rules still apply. Read-only credentials suffice for listing/import/fetch/pull; pushing needs permission to write repository contents, and GitHub may require additional workflow permission for workflow-file changes. Use repository-limited credentials where available. See [GitHub token guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).
3. In Projects, choose Import from GitHub, load the selected account's repositories or enter `owner/repository` or `https://github.com/owner/repository`. An optional project name controls a new, unique folder under the selected workspace. Importing copies the existing default branch and its history. No packages, project scripts or repository hooks run.

Only HTTPS `github.com` is supported. SSH, credential-bearing URLs, other hosts, URL redirects and URL query/fragment values are rejected. Imports need an existing nonempty default branch. Linking needs an ordinary project-root `.git` directory and an initial commit on a supported named branch; it does not initialise a plain project folder or change its existing origin. An existing remote pointing to a different repository prevents linking. Imported checkouts use Nakama's saved link and private tracking refs; Nakama does not install an origin/upstream configuration for external Git tools.

Linked worktrees, submodules, symlinks/junctions, hard-linked Git metadata, shared object stores, shallow/partial clones and unsafe/case-colliding paths are unsupported. Custom Git configuration, including repository hooks, credential helpers, filters, proxies, URL rewrites, monitors and configuration includes, prevents mutations. Ordinary branch, remote, author and basic repository settings are accepted. Git metadata inspection is bounded to 20,000 entries and imported/pulled tree listings to 4 MiB; use Git directly for unsupported repositories. Credential files are never selected for Nakama commit previews; secret detection is bounded and is not a substitute for reviewing the actual files.

## Daily flow

The project's GitHub panel shows its selected account and repository, current branch/HEAD, working changes and last-fetched ahead/behind counts. Refresh reads local status. Fetch contacts the linked account and updates only Nakama's tracking reference and object database; it does not change project files or staging. Counts are a snapshot of the last fetch, not live GitHub status.

Pull first requires a completely clean working tree and index, including untracked files. It fetches the matching remote branch and only allows a fast-forward. Dirty work, conflicts, divergence or unsupported tree entries stop the operation. Nakama never stashes, resets, rebases or resolves conflicts automatically.

For a local commit, choose 1–20 changed UTF-8 text files, enter a single-line message of at most 500 characters and an explicit author name/email. These identity fields become part of repository history. Review each file's exact before/after content, branch and HEAD. Previews allow 256 KiB per file version and 2 MiB total. They expire after ten minutes and bind the selected bytes, HEAD, index, configuration and project root.

Selected files that already have staged changes are rejected, preserving intentional partial staging. Unselected staged changes are allowed and remain staged. Creating the commit writes reviewed bytes without filters or line-ending conversion, advances the current branch using an expected old commit, updates only the selected index entries and leaves working files unchanged. It does not push, sign or run hooks. This is separate from local checkpoints, which leave the branch and entire index untouched. Repeating the same successful commit request returns its recorded receipt while the preview remains available.

If a ref update or staging finalisation has an uncertain result, Nakama retains `.git/index.lock` and `.git/nakama-commit-recovery.json` instead of discarding recovery information. Further mutations stop. Inspect the repository and these records with Git before repairing it; do not repeat the commit blindly. There is no automatic history rewrite or crash recovery that overwrites user work.

Review Push binds the selected account and repository, exact local commit, current branch and the remote branch's current commit (or absence for a new branch). The phone can request approval but cannot approve it. The approval warns about GitHub Actions and connected deployment services. Changing the local branch/index, account credential, link, remote branch or requester permissions invalidates the operation. A host restart loses volatile previews, so old requests require a new review and approval.

An existing remote must first be proved an ancestor of the exact reviewed local commit. The eventual push uses an explicit conditional `--force-with-lease=<branch>:<reviewed SHA>` as a compare-and-swap guard only after that proof. It never uses unconditional force or permits history replacement: a changed, deleted or newly created remote branch fails the lease. A remote that races to the same commit without exercising the lease is not reported as an approved update. A branch already equal during review returns an `up_to_date` receipt. The host checks the remote after transport and reports success only when GitHub confirms the exact target commit. An interrupted or rejected transport is unconfirmed; inspect GitHub before retrying.

Project workflows, repairs, checks, commands and file mutations cannot overlap a reserved Git mutation. Other applications can still change the checkout; changed state invalidates reviews, and Git's index/ref locks provide the final local write guard. GitHub transport uses the vault token only in transient child environment/private credential pipes. Tokens are not placed in URLs, process arguments, repository configuration, logs or persisted state. A fixed bundled helper is copied to a checked transient host-data folder, invoked with Node/Electron's Node mode and removed after the subprocess closes; repository-supplied helpers never run.

## API

Both project and Google access are required for paired Android callers. Windows owner access remains required to resolve a push approval. Chrome/MCP credentials cannot use these routes. The project state contains `github` link metadata and a `githubLastOperation` receipt; these fields are stripped from Google-disabled device state.

| Endpoint                                            | Request/result                                                                                                                                                                                            |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/github/repositories?accountId=...&page=1` | `{items:[{id,name,url,private,defaultBranch,updatedAt}],nextPage?}`. Explicitly loads the selected account's repository page.                                                                             |
| `POST /api/github/import`                           | `{accountId,repository,name?}` → `{project}`. Creates a new managed folder.                                                                                                                               |
| `GET /api/projects/:id/github`                      | `{linked,link?,status,busy}`. Link includes `accountId,accountLabel,repositoryId,repository,url,defaultBranch,private,linkedAt`. Status extends local Git status with optional `remoteHead,ahead,behind`. |
| `POST /api/projects/:id/github/link`                | `{accountId,repository}` → `{link}`. Does not change files or existing origin.                                                                                                                            |
| `POST /api/projects/:id/github/fetch`               | `{}` → `{projectId,status:'fetched',branch,head,previousHead,remoteHead,completedAt}`.                                                                                                                    |
| `POST /api/projects/:id/github/pull`                | `{}` → same receipt with `status:'pulled'`.                                                                                                                                                               |
| `POST /api/projects/:id/github/commit/prepare`      | `{paths,message,authorName,authorEmail}` → `{id,projectId,head,branch,message,authorName,authorEmail,files,expiresAt,disclosure}`. Files are `{path,kind,before,after,bytes}`.                            |
| `POST /api/projects/:id/github/commit`              | `{previewId}` → `{id,projectId,commit,head,branch,message,files,createdAt}`. `commit` is the new SHA; `head` is its previous parent.                                                                      |
| `POST /api/projects/:id/github/push/prepare`        | `{}` → `{id,projectId,head,branch,remoteHead,repository,accountLabel,expiresAt,disclosure}`. No external write.                                                                                           |
| `POST /api/projects/:id/github/push`                | `{previewId}` → `{approval}`. No push occurs until owner approval.                                                                                                                                        |
| `POST /api/approvals/:id/resolve`                   | Existing owner route `{approved:boolean}`. A completed push stores `approval.result` with `{projectId,status,repository,branch,head,previousRemoteHead,completedAt}`; status is `pushed` or `up_to_date`. |

Local text review and push previews are held only in host memory and expire. The saved project link is persistent; tokens remain in the existing vault. No real GitHub account writes are used as automated tests. Live account listing/import and an explicitly approved push remain user acceptance steps; disposable local Git repositories exercise transport/ref/index behaviour without publishing anything.

Implementation references: [Git credential helper protocol](https://git-scm.com/docs/gitcredentials), [Git push and explicit leases](https://git-scm.com/docs/git-push), [Git ref transactions](https://git-scm.com/docs/git-update-ref), [Git merge fast-forward rules](https://git-scm.com/docs/git-merge).
